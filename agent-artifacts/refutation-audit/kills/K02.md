# K2 [refuted 3/3]
manifest.json asserts a skipgram marginalization identity that the committed blend-v1 tables violate on 2854 of 4094 keys

file: data/corpus/blend-v1/manifest.json :: manifest.json `skipgram_convention` / build_corpus.build_blend (per-kind independent apportion)
verdict claimed: UNSUPPORTED (VERIFIED)

## label_claim
blend-v1/manifest.json states unconditionally: `"skipgram_convention": "skip(a,c) = sum_b trigram(a,b,c) (matches committed 1-skip31.txt)"`. PROVENANCE.md §4 repeats it as "**Skipgrams by marginalization**: `skip(a,c) = sum_b trigram(a,b,c)`. This is not an invention — it reproduces the committed `1-skip31.txt` **byte-exactly** ... which a test asserts."

## referent_reality
The identity holds EXACTLY on iWeb (0 of 4087 keys disagree — that is what the cited test `test_marginalize_matches_the_committed_production_skipgram_table` checks) but FAILS on the committed blend-v1 tables it is written into: 2854 of 4094 keys disagree, L1 = 4,702, max|diff| = 11. Cause: build_blend marginalizes pre-apportionment on real-valued shares, then apportions the trigram and skipgram tables INDEPENDENTLY to 1e9, so the two integer roundings do not commute. No test checks the identity on blend-v1 — TestCommittedBlend checks types/totals/charset/1-skip==1-skip31 but never re-marginalizes. Magnitude is negligible (L1/total = 4.702e-06), so this is a false manifest claim rather than a wrong number: a provenance assertion whose only verification is on the one corpus where it happens to be true.

## blast_radius
No registered number moves — 4.702e-06 relative L1 is far below any reported precision (gauges are printed to 3-4 decimals on percentages). The downstream risk is to REASONING, not arithmetic: `corpus_identity()` embeds this manifest's fields in `analyze --json` provenance blocks, and a future agent reading `skipgram_convention` as an established invariant of the shipped table (e.g. to justify substituting a re-marginalized skipgram table for the committed one, or to build a consistency gate on it) would be relying on a claim that is false for the production default. Low severity, correctly.
