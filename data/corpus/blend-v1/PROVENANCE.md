# `blend-v1` — provenance, weights, and what is *not* reproducible

The multi-source n-gram frequency blend. Generated by `keybo build-corpus`
(`src/keybo/data/build_corpus.py`), which exists because the previous corpus did **not**:
`data/corpus/*.txt` was imported as opaque data in 2024-12-15's first commit, and **no
generator script exists in any of the repo's 444 commits** — so those tables cannot be
regenerated, and the stated requirement ("*a frequency list which sums to 1/100 and uses many
different corpuses*") was met by neither the source count nor the totals.

This file is written by hand and describes the committed artifact; the machine-readable
equivalent is `manifest.json`, emitted by the same build.

**These files ADD a corpus; they do not replace one.** `data/corpus/{bigrams,trigrams,1-skip,
1-skip31}.txt` are untouched and still the production corpus. Switching production is a
separate, reviewable decision — see [What switching would change](#what-switching-production-would-change).

---

## 1. The honesty statement — read this first

| | |
|---|---|
| **Reproducible** | The `prose`, `code` and `reference` registers — 4 of the 5 *sources*, 50% of the *weight*. Re-running the generator on the same machine yields byte-identical tables **and** an identical `manifest.json` (verified by rebuilding and `cmp`, not by inspection). |
| **NOT reproducible** | The `iweb-anchor` register — 50% of the weight. |

The iWeb corpus (Davies 2018) is **licensed and non-redistributable**, and **no extraction
script was ever committed**, so the iWeb counts cannot be regenerated from source text. They
are consumed here as committed derived counts: an opaque **trust anchor**. Its SHA-256 is
recorded below, so its *identity* is verifiable — its *derivation* is not, and no hash can fix
that. Anything downstream that depends on the anchor inherits that unverifiability.

**Do not read this document as claiming a fully reproducible corpus.** It claims a *documented*
corpus with one *declared* unverifiable component. If you need full reproducibility, build the
anchor-free variant, which is a supported first-class mode:

```bash
keybo build-corpus --out /tmp/blend-no-anchor --no-anchor
```

That variant is 100% reproducible — and, per §5, it is also where the layout board moves most,
so it is the honest stress test rather than a lesser fallback.

Two further known limits, stated rather than buried:

* **Source scale.** The locally-built registers total ~40 MB of text, against iWeb's hundreds
  of millions of n-gram tokens. They are *registers*, not a general-English sample. This is
  precisely why the anchor keeps a plurality weight (§3) instead of being dropped.
* **Machine dependence.** `python-stdlib` is located through the *running interpreter* and
  `man-pages` through `/usr/share/man`, so both depend on the host. `manifest.json` records
  the resolved `root` of every source and `built_with_python`, which is what makes an identical
  rerun checkable rather than assumed.

## 2. Sources

Every component is named, its extraction rule documented, and its bytes + SHA-256 recorded.
The hash covers the *raw* concatenated source bytes in sorted-unit order, so it identifies the
inputs independently of any later change to an extraction rule.

|---|---|---|---|---|---|
| `repo-markdown` | prose | 44 | 717,013 | `071b178dcb20431a…` | 655,013 |
| `repo-latex` | prose | 12 | 103,901 | `f46a6e336abc23b2…` | 70,480 |
| `python-stdlib` | code | 633 | 6,923,454 | `ac37ab97557a36a1…` | 4,464,282 |
| `man-pages-man1+man8` | reference | 2,661 | 32,237,026 | `7317f159fab99428…` | 28,751,372 |
| `iweb-anchor`/`bigrams.txt` | anchor | — | 30,098 | `c61e6cbd2eed1bef…` | *committed counts* |
| `iweb-anchor`/`trigrams.txt` | anchor | — | 704,245 | `ffa77f3a38922f0a…` | *committed counts* |

Resolved roots (also in `manifest.json`, which carries the full 64-hex hashes):

* `repo-markdown`, `repo-latex` — the repo root.
* `python-stdlib` — `sysconfig.get_paths()["stdlib"]` of the interpreter running the build
  (this build: CPython 3.13.14).
* `man-pages-man1+man8` — `/usr/share/man`.

### Extraction rules

| source | rule |
|---|---|
| `repo-markdown` | All `*.md` tracked under the repo, sorted by path, excluding `data/corpus` and the transient directories `.git .venv venv .pytest_cache .ruff_cache build dist node_modules __pycache__ .mypy_cache .tox .eggs site-packages`. Fenced and inline code, URLs, table rows, and emphasis/link markup stripped (`strip_markdown`). Table rows are dropped because they are *data*, not prose. **The exclusion list is load-bearing:** without it the walk descends into `.venv/`, so merely having run the tests adds 15 vendored third-party `LICENSE.md` files to "repo prose" and the build stops being reproducible. A regression test pins this. |
| `repo-latex` | All `*.tex` tracked under the repo, sorted by path, with the same transient-directory exclusions. Comments, `equation`/`align`/`tabular`/`figure`/`lstlisting` environments, control sequences, and math/markup punctuation stripped (`strip_latex`). |
| `python-stdlib` | All `*.py` under the stdlib root, excluding `site-packages/` and `test`/`tests` directories, sorted by path. Docstrings and comments stripped (`strip_python`) — the prose *inside* code belongs to the prose register, and removing it is what makes this a genuinely distinct **code** register rather than a prose/code mix. |
| `man-pages-man1+man8` | Gzipped man pages in `man1` and `man8`, sorted by name. roff comments, metadata requests (`.TH`, `.de`, `.nr`, conditionals) and font/size escapes stripped, while the *argument text* of prose-bearing requests (`.SH`, `.TP`, `.B`, …) is kept (`strip_roff`). |
| `iweb-anchor` | **NOT REPRODUCIBLE.** Consumed as the committed `bigrams.txt` + `trigrams.txt`. Its skipgrams are re-derived from its own trigrams by marginalization (below) rather than read from `1-skip.txt`, so the whole blend uses one skipgram convention. |

## 3. Blend weights — and why these numbers

Declared per **register**; sources inside a register pool in proportion to their own n-gram
mass. Each register is first converted to a probability distribution over its *own* mass before
weighting, so a component's influence comes from its declared weight and **not** from how much
text it happened to contain. That property is what makes these numbers mean anything, and it is
covered by a test.

| register | weight | justification |
|---|---:|---|
| `anchor` | **0.50** | The iWeb component. Still the plurality, because it is the only component built from a *large, sampled, general-English* corpus; the locally-built registers are small and specialized. Halving it from an effective 1.00 is the actual change: **no single source can decide a ranking any more.** |
| `prose` | **0.25** | Locally-built English prose (repo Markdown + LaTeX). Reproducible, and the register a keyboard layout is genuinely for. |
| `code` | **0.15** | The programmer register the audit predicted would diverge materially — and did. A real but minority share: a general-purpose layout should *feel* this pull without being governed by it. |
| `reference` | **0.10** | Terse command/reference English — a third distinct register that is neither flowing prose nor code. |

**Prose-dominant with a declared technical share** (`prose` + `anchor` = 0.75 English prose;
`code` + `reference` = 0.25 technical). The weights are a stated editorial judgment, not a
measured optimum — which is exactly why they are a CLI flag:

```bash
keybo build-corpus --out /tmp/code-heavy --weights anchor=0.2 prose=0.2 code=0.5 reference=0.1
```

Weights are renormalized over the registers actually present, so naming an absent register
cannot silently steal mass. `manifest.json` records both `weights_declared` and
`weights_effective`.

## 4. Format and the "sums to 1/100" requirement

Each table sums to **exactly 1,000,000,000**:

| table | files | types | total |
|---|---|---:|---:|
| bigrams | `bigrams.txt` | 4,081 | 1,000,000,000 |
| trigrams | `trigrams.txt` | 114,920 | 1,000,000,000 |
| skipgrams | `1-skip.txt`, `1-skip31.txt` | 4,094 | 1,000,000,000 |

so `count / 1e9` sums to **1** and `count / 1e7` sums to **100** — both conventions are one
division away.

**Why not literally write fractions?** Because `load_frequencies` (`src/keybo/data/corpus.py`)
parses counts with `int()` and *silently skips* rows that fail, so a table of `0.0031`-style
shares would load as **empty** — a silent-wrong-answer bug, not an error. A large declared
integer total satisfies the requirement while staying loadable.

**This is a declaration, not a change of meaning.** Every ratio gauge already normalizes
internally — `kmstats.stats` divides by layout-restricted totals, `oxey.pattern_shares` by its
own corpus mass — so the absolute scale cannot move any ranking. The previous corpus's raw
counts were *numerically* equivalent; what they lacked was a *declared* total.

Other format properties, all pinned against the production loader:

* `ngram<TAB>count`, one per line, sorted by descending count then n-gram.
* **Space is a real character**, taken verbatim: `"e "` is a different bigram from `"e"`.
  Out-of-charset characters normalize to a space (a word boundary) rather than being deleted,
  so `foo(bar` cannot produce the false bigram `ob`.
* **Charset** = the 64 characters of the production tables: space + 52 ASCII letters +
  `" ' , - . / : ; < > ?` — the ANSI 30-key universe plus its shifted forms. **Case is
  preserved**, because the iWeb tables preserve it (95% of their bigram mass is lowercase, so
  case carries real signal). A lowercase-folded component could not be summed with the anchor,
  so every component uses this same universe.
* **Skipgrams by marginalization**: `skip(a,c) = sum_b trigram(a,b,c)`. This is not an
  invention — it reproduces the committed `1-skip31.txt` **byte-exactly** (4,087 entries,
  511,687,503 total, 0 mismatching keys), which a test asserts. The older `1-skip.txt` is a
  *different*, unreproducible pass; both filenames are emitted with identical content so the
  blend drops into either loader path (`analyze.py` reads `1-skip.txt`; other harnesses read
  `1-skip31.txt`).
* **Determinism**: nothing samples, so there is no seed. Sources are walked in sorted order,
  the largest-remainder apportionment breaks ties on the n-gram string, and rows sort
  deterministically. Same inputs → byte-identical output.

## 5. What switching production would change

Measured, not predicted: `state/build-corpus/artifacts/board_iweb_vs_blend.{py,out,json}`
re-runs the all-gauge board over 7 layouts × 15 corpus-sensitive gauges × 3 corpora.

**Distance from iWeb** (Jensen–Shannon, bits, on the space-free C30M subset the gauges see):

| corpus | JS(bigram) | JS(trigram) | verdict |
|---|---:|---:|---|
| `blend-v1` | 0.01492 | 0.04367 | moderately distinct |
| `blend-v1-no-anchor` | 0.05010 | 0.14648 | moderately distinct |

Neither is a relabelled iWeb copy, and neither is a wild outlier.

**How much the board moves** (vs iWeb-only):

| corpus | gauges reordered | pairwise inversions | winners changed |
|---|---:|---:|---:|
| `blend-v1` | 8/15 | 23/315 (7.3%) | 3 |
| `blend-v1-no-anchor` | 11/15 | 63/315 (20.0%) | 9 |

Under `blend-v1` the rank-1 layout changes on three gauges: `alt` (archive-1846 → keybo-lsb),
`redir` (lsb-sib → archive-1843) and `comfort` (keybo-lsb+lm → archive-1846). Seven gauges —
`sfr`, `sfb`, `sfs`, `sfs-dist`, `lsb`, `lsb-dist` and `sr-roll` — keep their full ordering
*unchanged*, which is a useful sanity signal: the blend is a *reweighting*, not noise.

**The decision-relevant number.** Corpus-sensitive axes the closure-3 flagship wins:

| incumbent | iweb-only | blend-v1 | blend-v1-no-anchor |
|---|---:|---:|---:|
| keybo-lsb | 9/15 | 10/15 | 11/15 |
| keybo-lsb+lm | 7/15 | 8/15 | 10/15 |
| lsb-sib | 11/15 | 11/15 | 11/15 |
| archive-1843 | 10/15 | 9/15 | **7/15** |
| archive-1846 | 11/15 | 10/15 | 9/15 |
| qwerty | 14/15 | 14/15 | 14/15 |

* **The flagship still beats archive-1846** — 11/15 → 10/15 → 9/15. The conclusion survives,
  but the margin narrows monotonically as iWeb's weight falls, so it is *corpus-conditional in
  degree*.
* **Against archive-1843 it inverts**: 10/15 → 9/15 → **7/15**, i.e. the flagship loses its
  majority under the fully reproducible anchor-free corpus.
* Symmetrically, the flagship gets *stronger* against keybo-lsb (9 → 11) and keybo-lsb+lm
  (7 → 10). keybo-lsb's `sfb` doubles (1.0784 → 2.2017) while the flagship's rises far less
  (1.2408 → 2.0926), so the two swap places: **keybo-lsb's iWeb `sfb` win was corpus-specific**,
  and that now shows up at a defensible blend weight rather than only under a 100%-code stress
  corpus. Note the direction — a *narrower* margin against archive-1846 comes with a *wider*
  one against keybo-lsb; the blend does not uniformly favour or disfavour the flagship.

### Gauge boundaries — what is *not* corpus-sensitive

Stated rather than silently omitted:

* **Corpus-invariant by construction**: `genkey`, `oxeylyzer-1`, `oxeylyzer-2`, `wfd`.
  `analysis/community.py` loads each from `data/community/vendored/*.json.gz`, and
  `community_suite(pinned)` takes **no corpus argument** — these ports score on their tools'
  own native corpora deliberately. They cannot move under a new blend, and a "blend" column for
  them would be fabricated. Reported once in the board output.
* **Not evaluated**: the measured speed surface (`analysis/timecard.py`). `models/` is empty,
  and a speed surface is a *model fit*, not a corpus reweighting — refitting it is out of scope
  here. Its absence is a scope boundary, not a result.

## 6. How to regenerate

```bash
# the committed blend (includes the non-reproducible anchor)
keybo build-corpus --out data/corpus/blend-v1

# fully reproducible variant — no anchor
keybo build-corpus --out /tmp/blend-no-anchor --no-anchor

# re-weight (shares are renormalized over the registers present)
keybo build-corpus --out /tmp/custom --weights anchor=0.4 prose=0.3 code=0.2 reference=0.1

# verify the board yourself
python state/build-corpus/artifacts/board_iweb_vs_blend.py
```

Tests: `tests/data/test_build_corpus.py` (41 tests) covers determinism, the production file
format, the declared total, weight arithmetic, charset handling, the byte-exact skipgram
convention, the anchor's honesty fields, and a round-trip through the real `load_frequencies`.
